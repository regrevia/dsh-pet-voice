# 端到端延迟预算：每一段谁负责、现在多少

手机说一句话 → 听见第一声回复，中间可以拆成六段。每段单独量过，加起来才知道「慢」到底慢在哪，也才知道该催谁。

| # | 段 | 现在（中位） | p95 / 尾巴 | 归谁 |
| --- | --- | --- | --- | --- |
| 1 | 手机 → 公网入口 TLS 建连 | 55 ms（首个字节 83 ms） | 偶发卡 **7.5 s**（SYN 丢了，TCP 重传阶梯）：60 次采样命中 1 次 | App（建连超时+重试）/ 网络 |
| 2 | 派发受理 ack | 540 ms | 1.2 s | 插件 / 宿主路由 |
| 3 | ASR 识别 | 486 ms | 556 ms | 语音 worker（mlx） |
| 4 | 模型首字（ack → 首个 delta） | **1801 ms** | 3248 ms | 上游模型，改不动，只能遮 |
| 5 | TTS 首字节（新句真合成） | **538 ms**（短句 n=5）/ 1638 ms（26 字长句） | 939 ms | 语音 worker（要换常驻 WS）；缓存命中 0.9–1.3 ms |
| 6 | 首句下发 → 悬浮窗出声 | 待测 | — | App（`PetLatency` 埋点在 132 里就有） |

上面四段是干净 n=10（无并发、无别的负载）量的；按 ack 540 + 首字 1801 + TTS 首字节 1163 加第 6 段估：**从松手到听见第一声约 3.5 s + App 侧出声**，目标是 2 s 以内。能砍的排序很清楚：5（1163 ms，全可控，常驻 WS 能压到 400 以内）> 1 的尾巴（7.5 s，偶发但体验极差）> 4（只能遮，不可控）。

## 会话列表：从 2.5 s 到 6 ms

手机上翻页/下拉刷新会连着打 `/api/sessions`，这条以前是隐藏的拖累：**每请求逐条** statSync + JSON.parse 全部 2415 条会话的投影，成本跟 limit 无关、跟会话存量线性涨。10 并发时 k=10 要 2511 ms。

改法是两件小事叠加：投影改成懒加载（便宜过滤 + 按 `updatedAt` 倒序，够 `limit+1` 条就停），列表页走 SWR（先给缓存再后台刷新；派发/解析仍走严格路径）。

| | 改前 | 改后 |
| --- | --- | --- |
| k=1 | 897 ms | 48 ms |
| k=5 | 1600 ms | 10 ms |
| k=10 | 2511 ms | **17 ms**（宿主实跑 6 ms 中位） |
| 压测 poll 段 p95 | 2674 ms | 99 ms |

顺带记住一件事：`list()` 那 0.5 s **不是扫盘**（readdir 全树 68 ms），是逐条读元数据。以后别再从「扫目录」方向找。

## 别再用旧的 delta 数字

`pet-bench` 原来只按 `event` 名认帧，可 SSE 上还同时广播着别的会话的事件——桌面端在别的会话里说话时，别人的 `delta` 会被当成本轮首个 delta。表现很迷惑：`delta` 中位 153 ms 而 `final` 1741 ms，自相矛盾。现在 start/delta/final/end 一律按 `data.sessionId` 归一后认领，并排除 `origin=desktop`。**以前那些「delta p95 23.4 s」有一部分是串帧串出来的，不是链路慢。**

## 已经排除的怀疑

- **不是本地反代慢**：本机 8443 打 30 次新连接，中位 4 ms，一次没卡；同样的 30 次走公网就有 1 次卡 7.5 s。所以慢在公网那一段，不在 Mac。
- **不是中转丢连接**：中转侧 `ListenDrops=0`、`BacklogDrop=0`，8443 监听队列没打满。
- **不是 ASR 退回 CPU**：`/health` 报 `backend=mlx-whisper device=gpu`，`/api/asr` 也照实透出；如果退回 CPU，bench 会直接标 ⚠ 并在 `--strict` 下退出 2。

## 各段的抓手

1. **建连尾巴**：App 把建连超时从 8 s 收到 2.5 s，失败立刻重试一次。SYN 丢失是概率事件，我们能做的是别等满 8 秒。
2. **ack**：路由要解析会话、拼上下文；和模型比它很小，暂时不动。
3. **ASR**：0.52 s 已经贴着 mlx 的推理极限（自报 0.516 s），还能动的是「少传一点音频」，收益有限。
   设备侧链路已单独打通（0.9.68 真机 `PetLatency` 日志）：按住 3.1 s 的 wav（97964 B）上传到宿主，日志里是
   `asr 208ms wav=97964B http=200`。这 208 ms 只说明**传输 + 空音频短路**有多快——那段录音是静音
   （`人声0ms`、`textLen=0`），服务端没跑识别，识别时延仍按表里 486 ms 记。
4. **模型首字**：唯一能遮的办法是出声前先给一句极短的语气词，代价是可能显得机械；暂时不做，等端到端数到位再判断。
5. **TTS**：缓存命中只要 1 ms —— 说明慢在每次现建连接 + 冷合成。2026-10-28 复测（`preset=whale`，本机 54279 直连）：
   短句（8–10 字）冷合成首字节 501/511/538/620/939 ms（中位 538 ms），26 字长句 1638 ms，
   同样的句子第二次请求 0.88/1.16/1.34 ms、字节数完全一致（21068 B）——所以冷合成的成本跟字数正相关，
   跟连接建立的一次性开销也有关，档位不是固定的 1.2 s。
6. **App 侧**：`PetLatency` 埋点（`preflight` / `tts 流已连上` / 首句）已经在 132 里，抓够 10 轮就能把 5→6 之间的缝补上。

## 待机 CPU：亮屏 ~0.9 个核，灭屏 ~5%（2026-10-28，0.9.68 真机）

`/proc/<pid>/stat` 的 `utime+stime` 在 5 秒窗口里前后差（USER_HZ=100）：

| 场景 | `com.whale.pet` | WebView sandbox | 合计 |
| --- | --- | --- | --- |
| 亮屏、桌宠待机在桌面 | 245 拍 ≈ 49% 单核 | 224 拍 ≈ 45% 单核 | ≈ 0.94 核 |
| 灭屏（`input keyevent 26`） | 19 拍 ≈ 3.8% | 8 拍 ≈ 1.6% | ≈ 5% |

线程归因：renderer 侧 CrRendererMain 11% / Media 7.4% / Chrome_ChildIOT 7.4% / CodecWorker 3.7% /
Compositor 3.7%；app 进程 main 18.5% / VizWebView 7.4% / Chrome_IOThread 7.4% / RenderThread 7.4%。
待机素材只有 `idle.webm 420x465 @10fps`，成本是**解码 + 每帧画布重绘 + 合成**。

已试并回滚：画布背衬 `dpr` 上限 2.5 → 1.5（每帧清像素 1.7M → 0.6M），实测 47.4% / 45.6%，
与改前无差别 ⇒ 像素填充不是瓶颈，别在这条路上再花时间；要降待机成本只能动解码或帧率。

灭屏自动停帧，没有息屏偷跑电的问题。量法与完整日志见 `local/evidence/round-summary.md` 第 7 轮。

## 宿主 → 气泡：say 通道（0.9.69 真机实测）

宿主侧 `POST /pet-voice/api/say`（Bearer，body `{text, voice?, id?}`）：`stripForSpeech` 后空的直接 400，
超 `SAY_MAX_CHARS` 截断，`voice` 不在白名单就退回默认音色，`saySeq += 1` 入队（队列超 `SAY_MAX` 丢最旧），
同 `id` 再发返回 `{ok, saySeq, queued, deduped:true}` 且不再上屏。

手机侧只有一个方向：`GET /pet-voice/api/say?since=<cursor>`。

| 参数 | 值 | 作用 |
| --- | --- | --- |
| `SAY_POLL_MS` | 1500 ms | 轮询间隔（页面没就绪时退到 3000 ms） |
| `SAY_MAX_PER_POLL` | 3 条 | 单轮最多搬几句子，避免一次刷满 |
| `since` 初值 | -1 | **只对齐游标、不回放历史**：进程起来不会把旧句子倒给你 |

实测（真机 15ca9736 / 0.9.69）：POST → `PetSay: 气泡上屏 1 条 cursor=N` 两条样本 **0.8 s、1.4 s**，
上限就是轮询间隔 + 一次 RTT；重复 `id` 后没有第二条 `PetSay`。熄屏 `stopSayPoll()`、亮屏 `startSayPoll()` 自动接上，
`onDestroy` 停；`pageReady` 之前不发请求。

成本：亮屏待机 `4492/5349` 5 秒 237 / 221 拍 ≈ **0.92 个核**，与 0.9.68 的 0.94 核在噪声内
⇒ 1.5 s 一次的小 GET 没有可测开销，别为它再加“省电”开关。

气泡几何没动：`#bubble` 定高 68 px、`-webkit-line-clamp:3`。**release 包没有 WebView CDP**，
机器可查的证据是 `logcat -d | grep PetSay` 那几行（截图只做人眼确认）。

## 量法

```bash
node scripts/pet-bench.mjs --n 8          # 2/3/4/5 段（会抢 local/pet-load.lock，抢不到 exit 3）
scripts/tts-bench.sh                      # TTS 首字节、连接建立、合成分开记
scripts/pet-size-check.sh                 # 顺带确认窗口尺寸没被延迟优化带歪
```

say 通道自检（发一句 → 手机上应有 `PetSay` 行；token 从文件读，不要打印）：

```bash
T=$(cat ~/.dsh/pet-voice/token)
curl -s -X POST http://127.0.0.1:54279/pet-voice/api/say \
  -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
  -d '{"text":"气泡自检","id":"manual-1"}'
adb shell "logcat -d | grep PetSay | tail -3"
```

公网那一段单量：

```bash
# 30 次新连接，看有没有卡在 7.5 s 的样本（打印里不含地址与 token）
for i in $(seq 1 30); do curl -sk -o /dev/null -H 'Connection: close' \
  -w "%{time_appconnect} %{time_total}\n" --max-time 10 "https://$HOST:8443/pet-voice/api/pair"; done
```

## 注意

- 两条负载脚本（bench / stress）**不能同时跑**，否则会往同一个安全会话排队，`delta` 会假涨到 20 s 级。锁文件 `local/pet-load.lock`，后到的直接 exit 3。
- 量延迟期间不要有别的 agent 在同一个宿主上跑重活，宿主进程是共享的，会污染 `state` / `sessions` 那几项。

## 气泡补记：0.9.70 游标修正 + 0.9.71–73 前台挂起（真机 15ca9736）

- **游标只推进到自己搬过的那条**（0.9.70）：宿主 `cursor` 是整批尾巴，连发 >3 句时直接用它会让中间几句永久跳过。
  5 连发实测：`气泡上屏 3 条 cursor=16` → 下一轮 `气泡上屏 2 条 cursor=18`，seq 全到。
- **App 在前台时先挂起**（0.9.71+）：悬浮窗在 App 前台是 `GONE`，此时上屏看不见，`offerSay` 记 `pendingSay`
  并只留最新一句；回桌面 250 ms 后 `回桌面补上屏`。真机：`05:20:48.999 气泡挂起 30 字` → `05:20:52.921 回桌面补上屏 30 字`。
- **App 内文字回复也走气泡**（0.9.72+）：`HistoryActivity.onAssistant(isFinal)` 调
  `FloatingPetService.sayToBubble(fullText)`，与宿主 say 共用 `offerSay`，不新增状态通道。
- 日志口径（0.9.73）：`气泡上屏 N 条` 只统计真正上屏的；挂起单独一行，别再把挂起当成功证据。
- 气泡视觉证据（release 包没有 WebView CDP，只能像素）：卡片带均值 45.4 vs 壁纸 157.2，
  亮像素文字行集中在 y=1358–1385；卡片几何仍是 68 px 定高。

### 气泡节奏（0.9.74，真机 15ca9736 pid 7317）

宿主不往手机推流，`GET /api/say?since=` 每 1500 ms 拉一次，一轮最多取 3 条；
0.9.74 起这 3 条不再同时塞进气泡，而是进本地队列一句一句上屏，
每句占 `min(9000, 3200 + 字数*90)` ms —— 与 JS 的停留公式同一口径。

实测相邻两句间隔 5.663 / 5.659 / 5.661 / 5.662 s（26 字，期望 5.54 s + 120 ms 余量），
4 字句 3.68 s、33 字句 6.29 s，抖动 < 10 ms。连发 8 句时队列上限 6 条、满了不推游标，
多出来的留在宿主队列下一轮取，因此「排空延迟」≈ 句数 × 停留时长，而不是 2 条/秒的换词。
代价是突发很长时最后一句可能晚十几秒才出现；这是「每句都读得到」的取舍，非缺陷。

### say 投递延迟：拉取间隔就是等待上限（0.9.75，真机 15ca9736）

`GET /api/say?since=` 是唯一的投递通道（App 侧 SSE 每轮重连、宿主无手机通道），
所以「宿主 POST 到气泡上屏」≈ 等到下一次轮询 + 250 ms 左右的本地上屏开销。

量法：host 侧记录 `POST` 发出时刻（`time.time()` 毫秒），与 logcat 里
`气泡上屏 N 字` 的时间戳相减；两端时钟差用括号法测（device 快约 225 ms，三次抖动 < 6 ms），
每次间隔 5.5 s 避免排队，各 5 个样本。

| 版本 | 拉取间隔 | 平均 | 最差 | 最好 | 空闲 CPU |
|------|----------|------|------|------|----------|
| 0.9.74 | 1500 ms | 659 ms | 1247 ms | 289 ms | 0.50 核 |
| 0.9.75 | 700 ms | 253 ms | 687 ms | 26 ms | 0.48 核 |
| 0.9.77 | 300 ms | **150 ms** | 264 ms | 37 ms | 0.49 核 |

间隔减半把平均等待砍掉 62%、最差砍掉 45%，而 CPU 没有可测变化（差 0.02 核在噪声内）：
空闲时轮询线程拿不到条目就直接睡，真正的成本在精灵解码，不在这次 GET。

0.9.77 再收一档（700 → 300 ms）：5 个样本 151 / 37 / 202 / 97 / 264 ms，
平均 150 ms、最差 264 ms，比 0.9.75 的平均 253 / 最差 687 再降；
空闲 CPU 0.488 核（0.9.76 基线 0.482，+0.6%），远低于「涨过 0.05 核就回滚」的闸门，故保留 300 ms。
再往下没有意义了：150 ms 已经落在一个 loopback 往返加一次气泡重绘的底噪里，
真正的大头是宿主那一侧的模型首字（第 4 段 1801 ms），不是这条 GET。
