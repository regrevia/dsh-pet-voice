# 端到端延迟预算：每一段谁负责、现在多少

手机说一句话 → 听见第一声回复，中间可以拆成六段。每段单独量过，加起来才知道「慢」到底慢在哪，也才知道该催谁。

| # | 段 | 现在（中位） | p95 / 尾巴 | 归谁 |
| --- | --- | --- | --- | --- |
| 1 | 手机 → 公网入口 TLS 建连 | 55 ms（首个字节 83 ms） | 偶发卡 **7.5 s**（SYN 丢了，TCP 重传阶梯）：60 次采样命中 1 次 | App（建连超时+重试）/ 网络 |
| 2 | 派发受理 ack | 540 ms | 1.2 s | 插件 / 宿主路由 |
| 3 | ASR 识别 | 486 ms | 556 ms | 语音 worker（mlx） |
| 4 | 模型首字（ack → 首个 delta） | **1801 ms** | 3248 ms | 上游模型，改不动，只能遮 |
| 5 | TTS 首字节（新句真合成） | **538 ms**（短句 n=5）/ 1638 ms（26 字长句） | 939 ms | 语音 worker（要换常驻 WS）；缓存命中 0.9–1.3 ms |
| 6 | 首句下发 → 悬浮窗出声 | 待测 | — | App（`PetLatency` 埋点在 132 里就有） |

上面四段是干净 n=10（无并发、无别的负载）量的；按 ack 540 + 首字 1801 + TTS 首字节 1163 加第 6 段估：**从松手到听见第一声约 3.5 s + App 侧出声**，目标是 2 s 以内。能砍的排序很清楚：5（1163 ms，全可控，常驻 WS 能压到 400 以内）> 1 的尾巴（7.5 s，偶发但体验极差）> 4（只能遮，不可控）。

## 会话列表：从 2.5 s 到 6 ms

手机上翻页/下拉刷新会连着打 `/api/sessions`，这条以前是隐藏的拖累：**每请求逐条** statSync + JSON.parse 全部 2415 条会话的投影，成本跟 limit 无关、跟会话存量线性涨。10 并发时 k=10 要 2511 ms。

改法是两件小事叠加：投影改成懒加载（便宜过滤 + 按 `updatedAt` 倒序，够 `limit+1` 条就停），列表页走 SWR（先给缓存再后台刷新；派发/解析仍走严格路径）。

| | 改前 | 改后 |
| --- | --- | --- |
| k=1 | 897 ms | 48 ms |
| k=5 | 1600 ms | 10 ms |
| k=10 | 2511 ms | **17 ms**（宿主实跑 6 ms 中位） |
| 压测 poll 段 p95 | 2674 ms | 99 ms |

顺带记住一件事：`list()` 那 0.5 s **不是扫盘**（readdir 全树 68 ms），是逐条读元数据。以后别再从「扫目录」方向找。

## 别再用旧的 delta 数字

`pet-bench` 原来只按 `event` 名认帧，可 SSE 上还同时广播着别的会话的事件——桌面端在别的会话里说话时，别人的 `delta` 会被当成本轮首个 delta。表现很迷惑：`delta` 中位 153 ms 而 `final` 1741 ms，自相矛盾。现在 start/delta/final/end 一律按 `data.sessionId` 归一后认领，并排除 `origin=desktop`。**以前那些「delta p95 23.4 s」有一部分是串帧串出来的，不是链路慢。**

## 已经排除的怀疑

- **不是本地反代慢**：本机 8443 打 30 次新连接，中位 4 ms，一次没卡；同样的 30 次走公网就有 1 次卡 7.5 s。所以慢在公网那一段，不在 Mac。
- **不是中转丢连接**：中转侧 `ListenDrops=0`、`BacklogDrop=0`，8443 监听队列没打满。
- **不是 ASR 退回 CPU**：`/health` 报 `backend=mlx-whisper device=gpu`，`/api/asr` 也照实透出；如果退回 CPU，bench 会直接标 ⚠ 并在 `--strict` 下退出 2。

## 各段的抓手

1. **建连尾巴**：App 把建连超时从 8 s 收到 2.5 s，失败立刻重试一次。SYN 丢失是概率事件，我们能做的是别等满 8 秒。
2. **ack**：路由要解析会话、拼上下文；和模型比它很小，暂时不动。
3. **ASR**：0.52 s 已经贴着 mlx 的推理极限（自报 0.516 s），还能动的是「少传一点音频」，收益有限。
   设备侧链路已单独打通（0.9.68 真机 `PetLatency` 日志）：按住 3.1 s 的 wav（97964 B）上传到宿主，日志里是
   `asr 208ms wav=97964B http=200`。这 208 ms 只说明**传输 + 空音频短路**有多快——那段录音是静音
   （`人声0ms`、`textLen=0`），服务端没跑识别，识别时延仍按表里 486 ms 记。
4. **模型首字**：唯一能遮的办法是出声前先给一句极短的语气词，代价是可能显得机械；暂时不做，等端到端数到位再判断。
5. **TTS**：缓存命中只要 1 ms —— 说明慢在每次现建连接 + 冷合成。2026-10-28 复测（`preset=whale`，本机 54279 直连）：
   短句（8–10 字）冷合成首字节 501/511/538/620/939 ms（中位 538 ms），26 字长句 1638 ms，
   同样的句子第二次请求 0.88/1.16/1.34 ms、字节数完全一致（21068 B）——所以冷合成的成本跟字数正相关，
   跟连接建立的一次性开销也有关，档位不是固定的 1.2 s。
6. **App 侧**：`PetLatency` 埋点（`preflight` / `tts 流已连上` / 首句）已经在 132 里，抓够 10 轮就能把 5→6 之间的缝补上。

## 量法

```bash
node scripts/pet-bench.mjs --n 8          # 2/3/4/5 段（会抢 local/pet-load.lock，抢不到 exit 3）
scripts/tts-bench.sh                      # TTS 首字节、连接建立、合成分开记
scripts/pet-size-check.sh                 # 顺带确认窗口尺寸没被延迟优化带歪
```

公网那一段单量：

```bash
# 30 次新连接，看有没有卡在 7.5 s 的样本（打印里不含地址与 token）
for i in $(seq 1 30); do curl -sk -o /dev/null -H 'Connection: close' \
  -w "%{time_appconnect} %{time_total}\n" --max-time 10 "https://$HOST:8443/pet-voice/api/pair"; done
```

## 注意

- 两条负载脚本（bench / stress）**不能同时跑**，否则会往同一个安全会话排队，`delta` 会假涨到 20 s 级。锁文件 `local/pet-load.lock`，后到的直接 exit 3。
- 量延迟期间不要有别的 agent 在同一个宿主上跑重活，宿主进程是共享的，会污染 `state` / `sessions` 那几项。
